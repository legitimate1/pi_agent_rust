本文记录哪些上游 Agent 工作流思想适合本 Fork。上游文件只是参考来源，不是本 Fork 的活动指令文件。只有在本 Fork 明确采用，或本地化写入自己的 `AGENTS.md` 和维护宪章后，一条规则才会在这里生效。

## 直接采用

以下是适合本 Fork 的通用维护原则：

- 用户指令优先于仓库默认规则；
- 删除文件必须获得明确许可；
- 危险 Git 和文件系统操作必须获得明确授权；
- 不要因为不熟悉某些改动的来源，就把它们当作可丢弃内容；
- 优先使用聚焦、可审查的编辑，不要盲目批量修改；
- 不要创建 `*_v2`、`*_improved` 等文件变体；
- 不确定库行为时，查阅第三方权威文档；
- 区分当前源码行为、设计意图和历史记录；
- 对质量、测试和发布声明要求证据；
- 工作未完成时留下有用的交接信息。

这些原则已经通过根目录 `AGENTS.md` 和本 Fork 的维护宪章生效。

## 本地化采用

### 分支策略

- **上游做法：** 所有工作遵循上游项目的分支策略。
- **本 Fork 决定：** 使用 `main` 进行上游同步，使用 `custom-next` 进行 Fork 开发。
- **原因：** 本 Fork 需要一个清晰的同步边界，而上游项目本身不需要这层边界。
- **生效位置：** 根目录 `AGENTS.md`、维护宪章、二开差异清单。

### 质量和发布流程

- **上游做法：** 使用上游项目的 DSR/RCH 质量和发布权威。
- **本 Fork 决定：** 不自动继承 DSR-only 或 RCH-only 要求。使用本 Fork 实际明确建立的 Cargo、本地验证、CI 和发布流程。
- **原因：** 上游环境中存在的工具和权威，不会自动在本 Fork 中可用或合适。
- **生效位置：** 根目录 `AGENTS.md`；详细命令要等新基线上的 Fork 流程明确建立后再补充。

### 产品方向

- **上游做法：** 上游产品目标和兼容性优先级指导实现。
- **本 Fork 决定：** 把上游产品方向作为参考，而不是自动成为本 Fork 的硬性要求。产品差异必须由用户选择的产品方向决定，并在发生差异时记录。
- **原因：** 产品分叉是产品决策，不是同步事故。
- **生效位置：** 未来的产品/设计文档，不属于当前引导治理层。

## 不作为本 Fork 活动规则采用

以下上游专属规则不会仅因为出现在上游文件中，就自动在本 Fork 生效：

- `/data/projects/AGENTS.md` 之类的上游外部规则文件；
- DSR 作为唯一质量、构建或发布权威；
- 上游环境中特有的 RCH 直接调用限制；
- 上游要求所有工作都在 `main` 上进行；
- 同步旧的 `master` 分支；
- 上游特有的 Beads、Agent Mail、`bv`、`ubs`、`cass` 或其他运维基础设施作为强制流程；
- 上游特有的性能、认证、证据或 reward-hacking 门禁；
- 上游特有的产品声明或发布术语。

这些内容以后可以研究或选择性采用，但必须先有明确的 Fork 决策和本地验证。

## 延后审查的事项

- 是否在未来的 `docs/upstream/` 目录保存一份不生效的上游 `AGENTS.md` 参考副本；
- 本 Fork 是否需要任务图或多 Agent 文件预约协议；
- 哪些上游质量实践可以在不引入整套上游基础设施的情况下，转化成本地轻量检查；
- 如何自动检测未登记的 Fork 差异。

在延后事项被正式决定之前，Agent 不得把它们当作隐藏要求。
