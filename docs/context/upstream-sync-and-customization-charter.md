# 上游同步与二开维护宪章

> 版本：0.1.0
> 状态：`custom-next` 引导版宪章
> 适用范围：`main`、`custom-next` 以及从 `custom-next` 创建的分支
> 最近审阅：2026-10-02

## 1. 目的

本宪章定义本 Fork 如何在保留明确二开行为的同时，持续贴近上游项目。目标是防止再次积累规模过大、没有记录、难以理解的上游差异。

本宪章管理仓库维护方式，不定义产品的运行时架构或功能集合。

## 2. 核心原则

### 2.1 上游是基线

本 Fork 从上游开始，并持续重新审查自己与上游之间的差异。旧 Fork 中曾经存在的实现，不会因为历史存在就自动被视为更正确。

### 2.2 每项差异都必须有意为之

每个长期存在的上游差异，都必须有明确原因、可定位的代码或配置边界、验证证据和生命周期状态。即使程序仍能构建，无法解释的漂移也属于维护缺陷。

### 2.3 小批量同步

不要求逐个合并每个上游提交，但**必须**足够频繁地审查和同步上游，使冲突保持在局部且容易理解的范围内：

- 开始新的非简单 Fork 功能前，先同步；
- 在正常维护周期内至少每周同步或审查一次；
- 当上游修改安全、依赖、持久化、协议、构建工具，或修改当前活跃 Fork 变更涉及的文件时，应更早同步；
- 如果有意延迟同步，必须记录延迟原因、下一次预定审查时间和阻塞条件。

延迟同步必须是显式例外，不能成为不可见的长期状态。

### 2.4 证据优先于历史假设

当前源码和测试决定当前行为。旧版 `docs/context/`、旧提交和旧 `custom` 分支只能作为迁移参考，不能证明相同功能已经存在于 `custom-next`。

### 2.5 小型、可重放的二开变更

每项二开变更都应该能够独立理解、测试、移除或重新应用。避免大范围格式化、顺手重构、复制整个上游流程，以及混合多个无关主题的修改。

### 2.6 基线和提交记录的含义

上游同步至少要区分以下几种提交记录，不得把它们统称为一个“基线”：

- **上游比较基线（`upstream baseline SHA`）**：用于判断 Fork 与上游差异的上游精确提交。二开差异的语义比较基线始终是它，不能用本地提交替代。
- **`main` 整合提交（`main integration commit`）**：把上述上游提交整合进本地 `main` 的提交。它可能包含本 Fork 允许保留的治理例外，因此不是上游提交本身。
- **`custom-next` 集成/基线提交（`custom-next integration/base commit`）**：记录这次同步结果进入 `custom-next` 的位置。如果 `custom-next` 是直接从更新后的 `main` 创建的，就记录创建时的基线提交，不得虚构一个不存在的合并提交。
- **`custom-next` 当前 tip**：二开主线当前最新提交，仅表示分支位置，不等于上游比较基线。

推荐在差异清单中使用明确字段名：

```text
upstream_baseline_sha
main_integration_commit
custom_next_integration_commit 或 custom_next_base_commit
current_custom_next_tip
```

其中，上游 SHA 是“比较基线”，本地 `main` 和 `custom-next` 提交是“可复查的整合位置”。

## 3. 分支契约

```text
upstream/main
     │
     ▼
main                 上游基线 + 已批准的 Fork 治理例外
     │
     ▼
custom-next          当前 Fork 二开主线
     │
     └── custom/*     聚焦的功能或修复分支
```

### `main`

- 尽可能贴近 `upstream/main`，同时保留本 Fork 已批准的治理例外。
- 只接收上游同步。
- 不接收产品功能、旧二开功能或普通 Fork 修复。
- 如果某项 Fork 专属基础设施是为了防止上游自动化在本 Fork 中错误运行，可以保留；但必须记录在二开差异清单中。

### `custom-next`

- 是当前 Fork 的二开主线。
- 通过聚焦的功能或修复分支接收二开修改。
- 只有在 `main` 已更新后，才从 `main` 接收上游变化。
- 不能被当作干净的上游镜像。

### 旧 `custom`

- 在引导阶段只作为历史参考。
- 只有在 `custom-next` 上重新实现并验证后，旧分支中的功能才算迁移完成。
- 未重新核查前，不得把旧版上下文文档复制到新上下文层。

## 4. 同步流程

正常顺序是：

1. 确认工作区和分支状态，保留无关的本地工作。
2. 抓取 `upstream/main`。
3. 更新 `main`，保留已经记录的 Fork 治理例外。
4. 记录本次上游提交的精确 SHA，并将它作为本次同步的上游比较基线。
5. 在本地 `main` 中整合上游变化，记录产生的 `main` 整合提交；本地治理例外不得被误记为上游内容。
6. 用户授权仓库更新后，推送更新后的 `main`。
7. 切换到 `custom-next`。
8. 将更新后的 `main` 合并到 `custom-next`，记录 `custom-next` 的集成提交；如果是从 `main` 直接创建分支，则记录 `custom-next` 基线提交。
9. 对每个冲突查阅二开差异清单，并检查新的上游行为。
10. 判断每项受影响的二开是仍然需要、需要适配，还是应该退役。
11. 运行针对性验证，更新差异清单，并记录未解决事项。

每次完成上游同步后，必须更新差异清单的全局同步状态：

- 当前上游比较基线 SHA；
- 本地 `main` 整合提交；
- `custom-next` 集成提交或基线提交；
- 最近同步时间；
- 当前 `custom-next` tip（如需要复查分支位置）。

但是，不能机械地把所有二开条目的“最近复核上游 SHA”改成新的上游 SHA。只有实际检查过的条目才能更新：

- 已检查且确认不受影响：更新复核 SHA，影响标记为 `unaffected`；
- 检查后需要适配：更新复核 SHA，影响标记为 `adapted`；
- 已被上游替代：更新复核 SHA，状态改为 `upstream-equivalent`；
- 尚未检查：保留旧复核 SHA，并标记为 `needs-review`。

Git 报告合并成功，并不等于同步完成。只有当全局同步状态、受影响的 Fork 差异和验证状态都已经登记，才可以认为同步完成。

## 5. 差异分类

每项 Fork 专属修改使用一个主要分类：

- **`new`** — 上游没有的新增能力；
- **`override`** — 有意改变上游行为或默认值；
- **`adaptation`** — 环境、平台、发行或集成适配；
- **`backport`** — 将选定的上游修改应用到不同的 Fork 基线；
- **`temporary`** — 有明确移除条件的短期 workaround；
- **`governance`** — Fork 所需的分支、自动化、文档或维护策略。

`temporary` 差异必须写明移除条件。`governance` 差异必须说明为什么上游行为在本 Fork 中不安全或不合适。

## 6. 差异边界

优先按以下顺序选择实现边界：

1. 具有窄接口的新模块或新文件；
2. 注册表、trait、策略、适配器、hook 或配置边界；
3. 上游入口处的小范围集成修改；
4. 只有在前述边界不可行时，才直接修改上游内部实现。

不要把逐行 `CUSTOM` 注释作为主要追踪手段。应使用分支、提交历史和二开差异清单。只有在需要解释不明显的运行时决策时，才在代码中添加本地注释。

## 7. 提交和审查契约

Fork 提交应该小而明确，并使用清晰前缀：

```text
custom: ...
custom-fix: ...
custom-docs: ...
upstream-sync: ...
```

一次提交不应同时包含：

- 上游同步和新的 Fork 功能；
- 无关格式化或重命名和行为变更；
- 临时实验和永久策略；
- 多个本可独立移除、但没有清晰理由的二开差异。

集成前应检查变更文件、相关测试和二开差异清单条目。Git 合并干净不能代替审查。

## 8. 冲突处理

当上游代码和 Fork 代码冲突时：

1. 通过差异 ID 找到对应二开；如果找不到，就标记为未登记差异。
2. 一起阅读上游修改和本地行为。
3. 检查上游是否已经提供等价能力或更好的扩展点。
4. 只有当二开的原因和当前价值仍然成立时，才保留本地行为。
5. 没有明确的本 Fork 需求时，默认优先采用上游行为。
6. 如果仍需保留差异，就按照新的上游边界适配，并更新其文件、测试、状态和移除条件。
7. 如果差异已经过时，在条件允许时通过独立、可审查的变更退役它。

Agent 不得静默地选择任意一侧解决冲突，然后报告同步完成。

## 9. Agent 维护协议

### Fork 修改前

- 确认分支和工作区状态。
- 读取本文和二开差异清单。
- 重新搜索当前源码和上游源码，确认上游是否已经提供目标能力。
- 对修改分类，并确定接入边界。
- 说明预期修改文件、测试和差异清单条目。

### Fork 修改中

- 保持范围聚焦。
- 保留无关工作。
- 避免整体复制上游子系统。
- 让测试靠近它们保护的行为。
- 不凭记忆更新项目事实文档；必须基于新基线核实。

### Fork 修改后

- 先运行范围最窄但有意义的验证。
- 记录真实结果，包括未运行或被阻塞的测试。
- 在声明差异已被追踪前，先更新二开差异清单。
- 获得授权后使用聚焦的提交信息提交。
- 留下交接，说明上游基线、Fork 差异、验证结果和剩余不确定性。

## 10. 例外处理

只有在遵循正常流程会造成更大即时风险时，才允许例外，例如紧急安全修复或阻塞发布的上游回归。例外记录必须说明：

- 延迟了哪条正常规则；
- 为什么必须例外；
- 还剩下哪些具体工作；
- 什么时候复查；
- 影响哪个分支和哪些文件。

例外不代表获得了执行危险 Git 操作或删除文件的授权。

## 11. 引导阶段边界

本版本有意不一次性决定所有未来政策。以下内容仍然是独立工作：

- 基于新上游基线重建项目架构和功能上下文；
- 决定旧 `custom` 中哪些功能应该迁移；
- 在新基线之上确定 Fork 最终的 CI 和发布流程；
- 决定哪些 Fork 功能应该贡献回上游；
- 自动检测上游漂移和未登记二开差异。

在这些决定完成前，Agent 必须记录不确定性，不得自行把推测写成项目政策。
