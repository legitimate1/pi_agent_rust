# SDK Drop-In 决策：退役严格契约对等性（RETIRE Strict Contract Parity）

**Bead**：bd-lnmtp.3.1 (G06-T1)  
**日期**：2026-04-17  
**决策**：RETIRE（退役）严格的 SDK drop-in 声明

## 执行摘要

在对 SDK 契约（`docs/dropin-sdk-contract.json`）与实际实现（`src/sdk.rs`，2455 行）进行全面分析后，决定**退役严格的 SDK drop-in 声明**，转而追求功能对等。

## 关键分析发现

### 契约与现实的差距

契约显著低估了当前实现状态：

| 能力 | 契约声明 | 实际状态 |
|------|----------|----------|
| SDK-01（会话工厂） | 缺失 | ✅ `create_agent_session()` 已实现 |
| SDK-02（提示词流式） | 部分 | ✅ `prompt()`、`continue_turn()` 已完成 |
| SDK-03（steer/followup） | 部分 | ✅ `steer()`、`follow_up()` 位于 RPC 层 |
| SDK-04（事件订阅） | 部分 | ✅ `subscribe()`/`unsubscribe()` 已完成 |
| SDK-05（模型控制） | 部分 | ✅ `set_model()`、`set_thinking_level()` 已完成 |
| SDK-06（会话管理） | 缺失 | ❓ `switch_session()`、`fork()` 已存在 |
| SDK-07（压缩/中止） | 部分 | ✅ `compact()`、abort 方法已完成 |
| SDK-08（工具/钩子） | 部分 | ✅ 已实现丰富的工具工厂 |
| SDK-09（传输适配器） | 缺失 | ❓ RPC 客户端已存在，需验证 |
| SDK-10（契约稳定性） | 已实现 | ✅ 稳定的 `pi::sdk` 模块 |

**10 项能力中有 7 项实际上已实现或接近完成**，而非文档所述的“3 项缺失、6 项部分”。

### 严格对等方案的核心问题

1. **文档债务大于实现债务**：主要差距是过时的契约文档，而非缺失的功能
2. **API 形态 vs 功能对等**：严格镜像 TypeScript API 增加了实现复杂度，却没有明确价值。Rust SDK 使用符合 Rust 习惯的模式提供了等效能力（Result 类型、所有权/借用区分、async/await）
3. **维护负担**：维持与 TypeScript 的精确对等需要持续的同步投入，这些精力本可用于功能开发
4. **阻塞下游工作**：该决策 Bead 阻塞了 3 个下游 issue；退役严格声明可让实际进展得以推进

## 决策理由

### 退役（RETIRE）原因：

- **已实现功能对等**：核心智能体会话、流式、事件、工具、模型控制均已等效可用
- **更偏好 Rust 习惯用法**：`Result<T>` 错误处理、`Arc<T>` 共享、结构化并发模式比 TypeScript API 形态提供了更好的人体工学
- **资源分配**：工程投入更应花在功能/性能上，而非 API 形态同步
- **用户体验**：SDK 使用者关心的是能力，而非 API 语法是否一致

### 所需后续动作：

1. **更新契约文档**以反映实际实现状态
2. **创建功能对等验证测试**，替代 API 形态测试
3. **为 TypeScript → Rust SDK 使用者编写迁移指南**
4. **以功能对等方式关闭被阻塞的下游 Beads**

## 后续实施路径

- **兼容性**：为跨语言集成保持 RPC 协议兼容

## 结论

严格的 SDK drop-in 声明带来的问题多于其解决的问题。Rust SDK 已以符合习惯的形式提供了等效功能。退役严格声明可让人聚焦于真正的价值交付，同时保持功能等效。
