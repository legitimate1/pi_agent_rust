# 扩展平台项目治理

本文档定义 Pi 扩展平台的归属、决策权限、质量门禁与维护节奏。

---

## 归属

| 领域 | 负责人 | 备份 |
|------|-------|--------|
| 运行时（PiJS、QuickJS、宿主调用） | 主维护者 | 智能体复核（Claude/Codex） |
| 扩展 API 表面 | 主维护者 | 智能体复核 |
| 能力策略（safe/balanced/permissive） | 主维护者 | 需安全复核 |
| CI/CD 流水线 | 主维护者 | 通过门禁晋升自愈 |
| 一致性语料（223 个扩展） | 通过一致性 harness 自动化 | 新失败项人工分流 |
| 文档 | 主维护者 + 智能体 | 自动化陈旧检查 |
| 兄弟 crate（asupersync、rich_rust、charmed、sqlmodel） | 独立版本化 | 通过 Beads 依赖跨仓库协调 |

### 决策权限

- **扩展 API 的破坏性变更**：需主维护者批准。发布前记录于 CHANGELOG.md。
- **能力策略变更**（新增/移除能力）：需安全复核与一致性回归检查。
- **新增官方扩展**：必须在 Tier 1-2 级别通过一致性检查，并具备干净的预检报告。
- **依赖新增**：必须通过 `cargo audit`，新依赖中不得包含 `unsafe`。

### 发布门禁（1.0 标准）

依据 [releasing.md](releasing.md)：

- 在 Linux/macOS/Windows 上 CI 均为绿色
- 核心 CLI 模式稳定（print + interactive + RPC）
- 扩展运行时表面与安全策略稳定
- 发布阈值下一致性门禁达标

### 功能变更的完成定义

功能表面 PR（运行时/提供方/工具行为变更）在以下条件满足前不可合并：

1. PR 正文包含单元、端到端与扩展验证的已勾选证据。
2. PR 正文直接链接到这些运行的结构化产物/日志。
3. PR 正文包含通过验证与最近失败路径的可复现命令。
4. PR 正文不含未解决的清单占位符。

规范清单来源为 `.github/pull_request_template.md`，并在 Linux PR 流水线中由 CI 强制执行。

#### 存量功能分支的迁移指引

1. 基于最新 `main` 变基。
2. 将 PR 正文替换为 `.github/pull_request_template.md`。
3. 从最新 CI/本地运行回填证据链接。
4. 包含明确的失败路径产物链接及精确的重跑命令。
5. 重新运行 CI，仅在 DoD 防护通过后合并。

## 发布节奏

| 通道 | 频率 | 范围 |
|---------|-----------|-------|
| 补丁（`0.x.Y`） | 按需 | 缺陷修复、一致性改进 |
| 次版本（`0.X.0`） | 每月 | 新功能、API 新增 |
| 主版本（`X.0.0`） | 满足 1.0 标准时 | 稳定性承诺 |
| 预发布（`-rc.N`） | 主版本/次版本前 | 验证窗口 |

### 版本规则

- **SemVer**，标签格式为 `vX.Y.Z`（可信源：`Cargo.toml`）。
- 1.0 之前：允许破坏性变更，需记录于 changelog。
- 1.0 之后：破坏性变更需主版本升级并提供弃用窗口。
- 兄弟 crate 独立版本化。

完整发布流程见 [releasing.md](releasing.md)。

## 扩展治理

### 分级与审查

| 分级 | 数量 | 审查 | 一致性 |
|------|------:|---------|-------------|
| 官方 | 60 | 全量复核，MIT 许可已验证 | 要求 100% 通过 |
| 社区 | 58 | 自动化一致性检查 | 目标 90%+ 通过 |
| npm registry | 66 | 许可 + 溯源检查 | 尽力而为 |
| 第三方 | 23 | 溯源验证 | 尽力而为 |
| 智能体生态 | 1+ | 同社区 | 同社区 |

### 新增扩展

1. 扩展通过 `pi doctor` 且 verdict 为 PASS。
2. 许可为宽松类型（MIT、Apache-2.0、BSD）。
3. 溯源可固定（git commit 哈希或 npm 版本）。
4. 无需单扩展补丁（无修改兼容）。
5. 加入 `docs/extension-inclusion-list.json` 并分配分级。

### 移除扩展

- 扩展在以下情况下从语料中移除：
  - 许可变更为不兼容条款。
  - 源码不可用（溯源不可固定）。
  - 扩展需单扩展补丁才能运行。
- 移除记录于 CHANGELOG.md。

## 弃用策略

### 1.0 之前（当前）

- 允许破坏性变更，需在 CHANGELOG 中记录。
- 被弃用 API 至少在一个次版本内发出运行时告警。
- CLI 标志变更记录于 `--help` 输出。

### 1.0 之后（未来）

- 被弃用 API：告警持续 2 个次版本，在下一主版本中移除。
- CLI 标志移除：1 个次版本的弃用窗口。
- 扩展 API 变更：2 个次版本的弃用窗口。
- 能力策略变更：在发布说明中公告。

## 失能预案

本预案覆盖维护者失联、账号被入侵或出现发布阻塞紧急情况且主维护者无法直接操作仓库的场景。本预案有意保持流程化，不在仓库中存放密钥、私密联系方式、恢复短语或个人账户材料。

### 激活条件

仅当至少一项条件为真时使用此路径：

1. 主维护者在 72 小时内失联，且必须发布 Critical/High 安全修复、安装器损坏修复或发布阻塞回归修复。
2. 主维护者以书面形式明确委派紧急控制权。
3. GitHub 或 crates.io 账号疑似被入侵，需在轮换凭据期间暂停正常发布权限。

### 仓库归属升级

| 步骤 | 动作 | 证据 |
|------|--------|----------|
| 1 | 以标签 `operations` 创建紧急跟踪 Beads 并关联触发事件。 | `br show <id> --json` |
| 2 | 通过仓库外保存的维护者带外联系人名单确认激活条件。 | 紧急日志条目，不提交 |
| 3 | 由指定的紧急仓库管理员接受临时运营归属。 | GitHub 组织或仓库审计日志 |
| 4 | 冻结非紧急合并，直到 CI、发布标签与安装器分发完成验证。 | 分支规则集/审计日志快照 |
| 5 | 将每个动作记录于紧急 Beads，并在发布用户可见构建时记录于发布说明。 | Beads 评论、CHANGELOG 条目 |

私有名单必须至少明确两类紧急联系人：一名 GitHub 仓库管理员与一名发布/密钥操作员。若任一角色空缺，每周治理复核必须提交一个 P1 运营 Beads。

### 密钥恢复与轮换

仓库中不得包含任何密钥值。紧急操作员应在满足激活条件后，再从私有密钥管理器/托管中恢复或轮换凭据。

| 密钥或权限 | 恢复/轮换动作 | 验证方式 |
|---------------------|--------------------------|--------------|
| GitHub 仓库/管理员访问 | 轮换被入侵凭据，复核 SSH/GPG 密钥，撤销未知令牌，并确认分支规则集仍保护 `main`。 | GitHub 安全日志 + 规则集快照 |
| `CARGO_REGISTRY_TOKEN` | 撤销旧 crates.io 令牌，签发最小权限替代令牌，并更新 Actions 密钥。 | `Publish` 工作流试运行或预发布标签 |
| 发布工作流权限 | 验证 `.github/workflows/release.yml` 权限仍仅使用 GitHub 作用域的发布权限。 | 工作流运行日志 |
| 安装器产物完整性 | 在建议用户安装前，重新生成发布产物、`SHA256SUMS` 与 Sigstore/校验和证据。 | GitHub Release 产物列表 + 校验和证明 |
| 本地签名或恢复材料 | 在 Git 之外轮换，然后仅记录轮换事件与操作员身份。 | 私有托管审计日志 |

轮换后，作废所有紧急会话令牌，移除临时管理员，并在回归正常治理前捕获最终审计日志快照。

### 紧急发布流程

1. 基于最新 `main` 变基，保持补丁范围仅限紧急事项。
2. 运行 [AGENTS.md](../AGENTS.md) 中的强制本地门禁，包括 `cargo check --all-targets`、`cargo clippy --all-targets -- -D warnings`、`cargo fmt --check` 与 `./scripts/reconcile_beads_ledger.sh`。
3. 时间允许时先切预发布标签：`vX.Y.Z-rc.N`。
4. 依据 [releasing.md](releasing.md) 验证 `Publish` 与 `Release (GitHub binaries)` 工作流，包括安装器回归与校验和产物。
5. 仅在发布产物路径与安装器路径均通过冒烟测试后，再晋升至最终 SemVer 标签。
6. 在 `CHANGELOG.md` 与紧急 Beads 中记录紧急授权原因。

若 Critical/High 漏洞正被积极利用，紧急仓库管理员可绕过常规每月节奏，但不得绕过分支保护、代码复核证据或发布产物验证。

### 分支保护权限

仅主维护者或指定的紧急仓库管理员可变更分支保护、必需检查、发布工作流权限或标签保护。紧急期间，任何此类变更均需：

1. 关联的紧急 Beads。
2. 记录于 Beads 中的第二人或智能体复核。
3. GitHub 规则集或工作流权限差异的前后快照。
4. 紧急发布后立即恢复更严格规则。

在失能事件期间，不得为使无关工作可合并而放宽分支保护。

### 桌面推演

每季度或发布流程变更后运行一次本复核：

1. 挑选一个假设的 Critical 安装器回归场景。
2. 在不于 Git 中暴露联系方式的前提下，从私有名单中识别紧急仓库管理员与发布/密钥操作员。
3. 以演练方式走查 `CARGO_REGISTRY_TOKEN` 的凭据轮换：除非发生真实事件否则不实际轮换，但需验证负责人与存储位置已知。
4. 触发或检查一次不发布的发布预演，优先使用预发布标签或工作流试运行。
5. 确认安装器路径验证 `SHA256SUMS` 且已发布的安装命令从不传递安装器仅供测试的 `--no-verify` 标志。这与发布 runbook 中描述的凭据作用域 Cargo 上传不同。
6. 为任何缺失角色、陈旧密钥负责人、失败工作流或模糊的分支保护权限提交 Beads。

仅当每个角色均在私有托管中具名、发布工作流可在不发布最终版本的情况下预演、且无未跟踪的 Critical/High 运营缺口时，桌面推演才算通过。

## 事件响应

### 主干一致性回归

1. 在 24 小时内通过 `bv --robot-plan` + `br ready --json` 分流，并用 `br show <id>` 确认候选 ID 后再认领。
2. 若回归在运行时中：修复并发布补丁版本。
3. 若回归在测试 harness 中：修复 harness，重新运行战役。
4. 若回归在扩展中：以合理理由更新例外清单。

### 安全漏洞

1. 评估严重性（能力逃逸、沙箱绕过、数据泄露）。
2. Critical/High：48 小时内修复并发布补丁版本。
3. Medium/Low：在下一计划发布中修复。
4. 记录于 CHANGELOG.md 与发布说明。

### 性能回归

1. 对照 `budget_summary.json` 中的基线进行比较。
2. 若超出预算 >20%：发布前调查并修复。
3. 若超出预算 <20%：记录并在合理时调整阈值。
