# 上游同步工作区

> 这是 `docs/upstream/` 的当前入口。它记录分析窗口、语义波次、当前决策和完成证据；不复制源码 diff，也不把某次快照伪装成永久事实。
> 更新日期：2026-09-15

## 当前模型

```text
custom 上游起点 S ───────────────► upstream 分析终点 T
          （研究窗口，不等于一次性 merge）
                         ↓
              按语义依赖拆成功能闭包
                         ↓
              采纳 / 适配 / 冻结 / 排除
                         ↓
                 每波次独立验证
```

面对上千个上游提交，先确定终点，再分析 `S..T` 的最终净变化和宏观里程碑；不逐个提交机械处理，也不直接把最新 `upstream/main` 一次性吞入 `custom`。

## 快速规则

1. **先固定窗口。** 起点和终点都写成可复核的 SHA；移动 branch 只能作为候选引用。
2. **minor/tag 只做宏观锚点。** 版本边界帮助定位变化，不自动产生合并批次。
3. **先看净变化，再看因果。** 只对高价值、高风险或冲突主题定向回看历史。
4. **以闭包为单位处理。** 类型、实现、调用方、测试和必要文档要能够一起解释和验证。
5. **依赖与结构单独处理。** 依赖代际升级、extensions/VFS/核心 runtime 重构不能顺手带入普通波次。
6. **每波次都可停止。** 新失败无法归因、依赖漂移未决或跨越未设计边界时，停止扩大并记录。
7. **完成过的闭包不重复迁移。** Hub 等已在 custom 落地的能力，只处理相对当前实现的新增差异。

## Fork 边界

- `main` 只作为上游镜像基线，业务改动在 `custom` 完成；不要直接在 `main` 提交二开业务代码。
- 未经明确授权，不把上游 Dependabot 或其他会自动运行的上游机器人配置带入 `main`。
- 合并试验和大范围迁移使用隔离 worktree，不污染主工作区。
- `custom` 基线必须先验证；历史已知失败与新引入失败分开判断。

## 新一轮追踪的最小流程

```text
1. 刷新但不 merge 上游引用
2. 确认 custom 对应的 upstream 起点
3. 选择一个稳定 tag 或固定 SHA 作为分析终点
4. 统计 S..T 的净变化和 first-parent 里程碑
5. 识别功能主题、结构断点和依赖代际
6. 填写 wave-plan.md，逐波次决定采纳/适配/冻结/排除
7. 仅对准备处理的波次补读相关历史
8. 在隔离 worktree 中按波次执行 merge 或独立闭包移植
9. 每波次单独验证并记录证据
10. 验证稳定后，再更新当前同步基线
```

> 旧的 C1/checkpoint/inventory 体系已从活动文档中移除。历史事实若仍需追溯，应以 Git 历史和保留的完成证据为准；不要把旧快照的数字当作当前状态。
