# 改造式 Fork 的上游追踪与语义合并 SOP

> 适用：`custom` 已经发生结构重构、依赖分叉或行为定制，需要持续吸收上游变化的场景。
> 更新日期：2026-09-15

## 1. 核心原则

### 1.1 先定研究窗口，再定处理波次

面对上千个上游提交，不逐个提交机械合并，也不直接把最新 `upstream/main` 一次性 merge 到 `custom`。

先固定：

```text
S = 当前 custom 对应的上游起点
T = 选定的上游分析终点
```

然后分析 `S..T` 的最终净变化和宏观里程碑，再按语义依赖、功能闭包和结构边界拆分波次。`T` 是分析边界，不是一次性合并命令。

### 1.2 minor/tag 是观察锚点，不是自动批次

稳定 release、minor 版本和 first-parent 主线适合建立“从哪里到哪里”的时间线。但版本窗口内部可能同时包含 bugfix、依赖升级、功能闭包和架构重构，因此遇到独立语义或结构断点必须继续拆分。

反过来，一个功能闭包也可能跨越多个版本，需要作为一个完整波次处理。提交数量不是波次边界。

### 1.3 先看终点净变化，再定向回看历史

第一轮只回答：

- 起点到终点最终留下了哪些变化；
- 哪些变化属于同一主题；
- 哪些变化已经在 `custom` 中存在；
- 哪些变化与 custom 结构、依赖或行为冲突；
- 哪些变化明显无关。

只有对准备采纳、存在高风险或存在冲突的主题，才回看相关提交历史，补齐因果、前置 API 和功能闭包。不要为了获得确定感而读完整个上千提交区间。

### 1.4 合并载体服从语义，不预设只有一种方式

改造式 Fork 上，原始上游 commit 的文件锚点可能已经不存在，机械 cherry-pick 往往无法表达真实意图。默认优先考虑：

- 以功能闭包为单位的独立移植或适配；
- 在隔离 worktree 中对有限范围进行选择性 merge；
- 对于仍保持同一文件结构、确实独立且可验证的变化，才评估其他 Git 载体。

不能把“merge 是载体”简化成“必须全量 merge”。真正的规则是：选择能保留语义、可归因、可验证的载体。

## 2. 波次设计

每个波次必须满足：

1. 有明确的功能主题或结构主题；
2. 包含必要的类型、实现、调用方、测试和文档闭包；
3. 前置依赖已列明；
4. 能解释与 custom 现有实现的关系；
5. 有明确的采纳、适配、冻结或排除决定；
6. 完成后可以独立验证；
7. 失败时可以停止，不把未知问题带到下一波。

推荐的宏观检查顺序是：

```text
低风险基础修复
    ↓
依赖与底层 API（通常单独评估）
    ↓
核心契约 / runtime / 数据模型
    ↓
工具、provider、session 等功能闭包
    ↓
TUI 和外部集成
    ↓
extensions / VFS / 大型结构迁移
    ↓
生成物、快照、文档和收尾证据
```

这不是固定流程。如果某个修复依赖核心重构，应先处理其真实前置；如果一个 minor 周期没有结构断点，可以合并为较大的研究波次，但仍须保留语义边界。

## 3. 标准工作流

### 阶段 A：刷新引用并固定窗口（纯读）

```text
1. 刷新 upstream refs，但不 merge
2. 确认当前 custom HEAD 和对应的 upstream 起点
3. 选择稳定 release/tag 或固定 SHA 作为终点
4. 把 branch/tag 解析为不可变 SHA
5. 在 analysis-window.md 记录 S、T、日期和统计口径
```

不要把移动的 `upstream/main` 直接写成未经固定的终点。若必须以它作为候选，先记录观察 SHA，分析开始前再确认是否锁定。

### 阶段 B：建立宏观语义地图（纯读）

```text
1. 查看 S..T 的最终文件和行变化
2. 查看 first-parent 主线里的 release、架构和依赖里程碑
3. 按主题聚类：基础修复、依赖、核心、功能、结构、治理、生成物
4. 与 custom 当前能力对照：重复、互补、冲突、无关
5. 只为值得处理的主题补读相关历史
6. 把结果写入 wave-plan.md
```

最终 diff 是“终点状态”的证据；相关历史是“变化意图和前置关系”的证据。两者不能混为一个结论。

### 阶段 C：确定处理方式

对每个主题做一次明确决策：

- **采纳**：上游语义适合当前 custom，按闭包引入；
- **适配**：采纳上游目标，但按 custom 文件、接口或运行时重写；
- **冻结**：当前有价值但越过未准备好的结构/依赖边界，记录重新评估条件；
- **排除**：确认不属于当前 Fork 的产品目标或只是上游内部治理噪音。

### 阶段 D：在隔离环境执行

```text
1. 从 custom 创建临时 worktree/分支
2. 先验证 custom 基线
3. 一次只处理一个语义波次
4. 记录保留 custom、采纳 upstream、适配重写和冻结内容
5. 完成针对性验证
6. 将结果和证据写入波次记录
7. 通过后才开始下一波
```

worktree 是隔离手段，不是强迫全量 merge 的理由。独立闭包移植也必须保持同样的基线、验证和回退纪律。

### 阶段 E：收尾

只有在所有目标波次完成并且每波次都可归因后，才更新同步基线。失败时保留当前检查点和失败证据，不为了“追平数字”继续叠加下一波。

## 4. 冲突与漂移处理

| 情形                                     | 默认处理                                                  |
| ---------------------------------------- | --------------------------------------------------------- |
| custom 独有功能                          | 保留 custom，并记录为何不被覆盖                           |
| 已经在 custom 完成的同一功能             | 不重复迁移，只比较终点后的新增差异                        |
| 两侧同一功能但实现不同                   | 按行为契约和验证结果选择或适配，不按 ours/theirs 机械决定 |
| 测试快照、VCR、checksum、生成物          | 先判断来源，再重新生成或更新证据；不把冲突数量当语义价值  |
| 根配置和锁文件                           | 人工处理，版本和依赖决策必须记录                          |
| 主依赖/API 自动升级                      | 默认冻结；与适配代码组成独立波次                          |
| extensions、VFS、核心 runtime 等结构重构 | 默认冻结；先做独立设计                                    |
| 上游内部 Beads/swarm 或发布噪音          | 默认排除，除非 custom 明确需要                            |
| 无法归因的编译/测试失败                  | 停止扩大，先恢复可解释的基线                              |

### 依赖漂移是独立风险

Cargo.toml、Cargo.lock、build.rs 的变化可能文本上自动合入，却让 custom 代码面对新 API。不能因为 Git 没有冲突就接受它们。

主依赖升级必须回答：

- 上游哪些适配代码是配套的；
- custom 哪些模块受影响；
- 是否需要跨越当前冻结的结构边界；
- 是否能单独建立编译、测试和回退点。

没有这些答案时，保留 custom 依赖基线，并把升级记为冻结或独立迁移。

## 5. 验证门

### 合并前

- custom 基线验证完成；
- 起点、终点和波次范围已固定；
- 波次的功能闭包和停止条件已写明；
- 已知失败与本次新增失败的区分方法已确定。

### 每个波次后

- 针对性编译或测试通过；
- 关键行为契约有回归证据；
- 新增失败可以归因；
- 没有无记录的依赖、配置或生成物漂移；
- 波次记录写明实际采纳和保留内容。

### 大范围收尾

按项目 AGENTS 规定执行对应的全量测试、Clippy 和格式检查；不要把全量验证提前到尚未稳定的中间试验中，也不要用“能编译”代替功能和行为验证。

## 6. 停止条件

出现以下任一情况就停止当前波次：

- 需要自动引入未评估的主依赖代际；
- 需要修改 custom 的冻结结构，但没有独立设计；
- 失败无法区分是基线问题还是本波次问题；
- 波次已经混入多个无法独立解释的主题；
- 验证证据不足以证明行为保持；
- 继续处理只是在扩大冲突和上下文，而没有新增可归因信息。

停止不是失败，而是保留一个可解释的检查点，并把未处理内容记录为冻结、排除或待复审。

## 7. 当前项目的已知边界

- `custom` 是二开主线，`main` 只作为上游镜像基线；业务代码不直接提交到 `main`。
- 未经明确授权，不把上游 Dependabot 或其他会自动运行的机器人配置带入 `main`。
- Hub 最小闭包已经完成，详见 `plan-hub-minimal.md` 和 `docs/context/design-decisions.md` 的 D55。
- 全量 merge 探针的失败分析保留在 `probe-report-2026-08-29.md`；它是历史证据，不是当前终点。
- `known-test-failures.md` 是有日期的测试基线，重新使用前必须确认适用范围。

## 8. 追踪文档的维护规则

- 当前窗口只维护 `README.md`、`analysis-window.md`、`wave-plan.md` 和 `decision-log.md`。
- 完成证据单独放在保留的证据文档中，不重新伪装成待执行计划。
- 每次更新窗口时重新生成统计，不沿用旧 inventory 的数量。
- 旧方案可以通过 Git 历史追溯；若仍需保留历史分析，应明确标日期和“非当前依据”，不要与活动计划混放。
